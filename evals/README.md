# 评测集

检验 `physics-teacher` skill 是否按设计行为工作。

## 怎么用

本 skill 是纯提示词制品，没有可执行代码。所以「运行」指的是：

> 把用例的**输入**原样交给加载了本 skill 的 Claude，再把输出对照「必须做到 / 做了就算失败」逐条判定。

一次完整跑测 = 把 `cases.md` 里的 17 个用例各跑一遍，记录通过与否。
建议每改一次 `SKILL.md` 或 `references/` 就重跑一遍受影响的用例。

## 判定原则

**判定看行为，不看措辞。** 同一个意思换个说法是允许的；但「必须做到」的行为不能靠泛泛的话糊过去。

**「做了就算失败」比「必须做到」更重要。** 本 skill 的失败模式几乎都不是「答不出」，
而是**答得太满**——

- 缺题干时编一道题来审；
- 教师只要思路，却把整份教案写完；
- 不清楚某个理论的争议，却编一个争议出来填满栏目；
- 教案本来没什么大问题，却为了显得认真而凑出几个问题。

这些都不是能力不足，是**约束不足**。所以每个用例都配了一条明确的禁止项。

## 用例的来源

这些用例不是凭空造的，全部来自三轮实测中**真实暴露过的失效点**：

| 轮次 | 做了什么 | 挖出 |
|---|---|---|
| 第 1 轮 | 实跑复合请求（浮力公开课） | 5 条规则缺陷（时长冲突、传递规则缺失、门禁与编排打架、摘要粒度、附录压缩） |
| 第 2 轮 | 推演教练模式 | 3 条（先反问还是给方向、「怎么做」的粒度、选定方向后怎么走） |
| 第 3 轮 | 实跑 `pedagogy_theory` + `lesson_design_review` | 7 条（理论类「不知道就编」的 4 个出口、物理错误分级、伪探究检查项、门禁阈值） |

每一条缺陷现在都对应 `cases.md` 里的一个用例——**用例就是这些缺陷的回归测试**。

## 回归流程（改了规则之后怎么做）

**核心约定：每改一条规则，就重跑受影响的用例，并把结果记成一份 `baseline-*.md`。**

理由很直接——首次跑测就撞上了一次**规则之间互相打架**（摘要规则 vs §17 融合模板）。
那种缺陷读文档读不出来，改 A 动了 B 也看不出来，**只有跑才知道**。

### 跑多少：按改动范围定

| 改了什么 | 跑哪些 |
|---|---|
| 只改措辞、错别字 | 不用跑 |
| 改某条**规则** | 跑下表里对应的用例 |
| 新增 / 删除 task type | 跑受影响的用例，**并且全跑一次**（编号会动） |
| 准备发布 / 装进 Claude 前 | **全跑 16 个** |

### 规则 → 用例映射

改哪条规则，就跑哪些用例：

| 改的位置 | 受影响用例 |
|---|---|
| `SKILL.md` 输入材料门禁 | 01、02、03 |
| `SKILL.md` 编排协议（触发 / 展开 / 排序 / 摘要 / 传递 / 门禁优先 / 专业支持不编排） | 05、06、07 |
| `SKILL.md` 学段适配 | 15、16 |
| `SKILL.md` 行为边界 | 全部（尤其 11、13、14） |
| `SKILL.md` 面向新兴教师 | 11、16 |
| `references/workflows.md` §1（含时长规则） | 04 |
| `references/workflows.md` §12 / §13 教案诊断与修订 | 13、14 |
| `references/workflows.md` §14 设计教练 | 08、09、10 |
| `references/workflows.md` §15 内容拓展 | 15 |
| `references/workflows.md` §16 教育理论 | 11、12 |
| `references/output-templates.md` §17 融合方案 | 05、06、07 |
| `references/output-templates.md` 其余模板 §N | 对应的那个用例 |
| `references/physics-safety.md` 任何一段 | 13、16 |
| `references/physics-knowledge.md`（知识库内容或范围） | 17 |

### 记什么：`baseline-YYYY-MM-DD.md`

每次跑完新建一份，格式照 `baseline-2026-09-19.md`：

1. **表头写清这次改了什么**（否则过一个月就不知道在测什么）
2. 逐用例的判定 + **决定性证据**（引用输出里的原话，不要只写「通过」）
3. 失败详情节——失败点、失败原因、是不是规则打架
4. 结尾写已做的修复

同一天跑多次加后缀：`baseline-2026-09-20.md`、`baseline-2026-09-20-b.md`。

### 三种判定

| 判定 | 含义 | 怎么处理 |
|---|---|---|
| ✅ 通过 | 行为符合用例 | —— |
| ❌ 失败 | 行为不符合用例 | **必须处理**：要么改规则，要么改用例，并写明为什么 |
| ⚠️ 存疑 | 用例本身有问题（如 12 的逃生规则没被触发） | **改用例**，不要放过 |

### 什么算回归

**上次通过、这次失败 = 回归。** 回归几乎都指向「改 A 动了 B」，必须查清是哪一处改动引起的，不能直接重跑一遍当作没发生。

反过来，**上次失败、这次通过**也要记——那说明修复生效了。

## 已知的局限

这套用例由 Claude 自己编写、自己执行，**没有换一个模型实例去跑**。
所以它测不到一类失效：模型直接忽略某条规则。

真实部署后如果出现新的失效模式，把它补成新的用例——**用例库应该是长的**。
